# v3.7.18 全脚本复查：已确认问题与优化建议

后续状态：下列七类已确认问题已在 v3.7.19 修复，见 [修复与验证记录](audit-fixes-v3.7.19-2026-10-20.md)。本报告保留审计基线的原始表现；历史复现文件对应 v3.7.18，当前版本应运行 `tests/run.sh` 检查修复后的断言。文末设计优化建议仍按原范围单独记录，不等同于本次已修复缺陷。

基线：`fff189b681ea5df86f14e7d60aebdd16d7eb77fe`；日期：2026-10-20（北京时间）。前一轮到期日期污染 Xray 用户路由的问题已在此基线修复，本报告不重复将其列为未修复缺陷。

本轮检查主脚本及 nft 辅助脚本的用户管理、流量/到期限制、配置生成与回滚、版本更新、定时任务、机器人服务和卸载路径。对下列七类问题进行了本地隔离复现；没有登录服务器，没有触碰真实 Telegram、线上配置、防火墙或服务。本次只提交报告及复现文件，以下问题尚未修改业务代码。

## 1. P1：完整卸载仍可能停止其他网站的 Nginx

位置：`vless-server.sh:23147`，`do_uninstall` 中的其他站点判断。

代码仅统计 `sites-enabled`、`conf.d`、`http.d`，并排除路径含 `default` 的条目。其他站点若直接定义于 `nginx.conf`、自定义 include 目录或常用的 `default` 文件，可能被判断为没有其他站点。删除本脚本配置后，便停止、禁用整个 Nginx。

复现：隔离的 `nginx.conf` 有其他 server 块，另有本脚本的订阅配置；执行真实卸载函数的对应分支，使用私有路径和模拟服务命令，结果仍调用 `stop nginx`，其他站点配置仍存在。测试在后续服务/配置删除阶段前退出，没有执行真实卸载。

建议：完整卸载与订阅停用共用仅删除本脚本配置、校验并重载的逻辑。只有能确认服务所有权及完整有效配置时才考虑停止整个 Nginx。

## 2. P2：带前导零的流量配额可能变成无限额或错误数值

位置：`vless-server.sh:1623` 的 `db_set_user_quota`，以及 `db_add_user` 的配额转换。

菜单接受纯数字字符串，后端直接使用 Bash 算术。`08` 触发非法八进制运算后，配额仍以初始值 `0` 写入，函数返回成功，即变成无限额；`010` 按八进制转换成 8 GiB，而非预期的 10 GiB。各核心使用共享的用户配额入口，SS2022 同样受影响。

复现：`08` 返回 0、保存 0 字节；`010` 返回 0、保存 8589934592 字节。仅操作私有数据库。

建议：统一按十进制解析、设置数值范围，解析失败不修改原值；添加用户和修改配额复用同一校验函数。

## 3. P2：到期配置与定时任务的返回值契约不一致

位置：`vless-server.sh:1824` 的 `db_set_user_expire_date`、`:2118` 的 `ensure_expire_check_cron`、添加用户的到期任务调用。

- 取消到期限制时，数据库已保存为空，但函数最后的条件表达式返回 1，菜单提示“设置失败”。
- 到期 cron 新安装成功按现有契约返回 1；修改到期日期的调用方把它当成失败。复现中返回 1，但日期已更新。
- 添加用户的调用方又忽略该任务安装失败：模拟 cron 安装返回 2，新用户仍创建并返回 0。此时不能确认到期停用任务已经存在。

建议：调用方区分“已存在/安装成功/失败”，对外统一成功返回 0；取消限制正确返回成功；任务失败应明确提示已保存但尚未生效，或按事务恢复原配置。

## 4. P2：到期日期仅检查格式，非法日历日期也会保存

位置：`vless-server.sh:1824` 及 `_add_user`、`_set_user_expire_date` 的交互输入。

`YYYY-MM-DD` 正则不保证日期真实存在；后端也未验证日历值。隔离调用保存 `2026-13-40` 后返回 0。剩余天数解析可能失败，停用检查的字符串比较无法代表管理员原本想设置的到期时间。

建议：在写库前统一解析并回转比较日期，拒绝不存在的月份/日期；天数换算失败不能降级为空日期。保留空值和 `never` 的既有语义。

## 5. P1：手动清零后旧通知标记可能使下一次超额停用失效

位置：`vless-server.sh:1609` 的 `db_reset_user_traffic`，以及 `_sync_all_user_traffic_unlocked` 中两个核心的超额处理分支。

手动重置将 `used` 清为 0，但保留 `last_alert_percent=95`、`quota_exceeded_notified=true`。后续统计不仅用此标记去重通知，还将超额停用操作放在“通知尚未发送”的条件内部。

隔离复现完整路径：原用户超额并停用 → 管理员手动清零 → 重新启用 → 新流量再次超额 → 同步。结果为 `used=120, quota=100, enabled=true`；仅删除旧通知标记、保持用量不变再同步，立即变为 `enabled=false, disabled_reason=quota`。因此影响不仅是漏提醒，还可能使本轮配额失效。自动周期重置会清理旧标记，手动路径没有统一。

手动清零还会保留 `enabled=false, disabled_reason=quota`，用户不会因此自动恢复。这是当前的状态保留行为，应在界面提示“流量已清零，账号仍停用”；不应为了恢复超额用户而顺带启用人工停用或启动手动停止的核心。

建议：无论消息是否已送达，都独立执行超额停用检查；通知标记仅控制通知去重。手动清零同步清理上一轮告警标记，恢复账号采用独立的明确操作，保留人工停用和停止核心的状态边界。

## 6. P2：Telegram 空锁目录无法自行恢复

位置：`vless-server.sh:2723`，`_tg_poll_user_bot` 的 mkdir 锁。

进程在创建锁目录、写入 PID 前异常退出时，可能留下没有 `pid` 的目录。现有逻辑只恢复“有 PID 且该 PID 已消失”的锁；空锁永远返回 75。常驻循环对此每秒重试，不请求 Telegram，服务本身却可能仍显示运行。

复现：预置私有空锁目录，连续三次轮询返回 `75,75,75`，API 请求次数为 0。未连接 Telegram。

建议：复用已有的内核 flock 兼容封装；如保留目录锁，应有带创建宽限期的孤儿锁恢复，避免误抢正在初始化的锁，同时给长期争用增加可见日志。

## 7. P2：更新系统脚本失败也会提示同步成功

位置：`vless-server.sh:31610`，`perform_script_update` 的第二目标同步。

从下载目录运行脚本时，菜单会先更新当前文件，再复制到 `/usr/local/bin/vless-server.sh`；这次复制和授权失败均未判断，仍输出“已同步更新系统目录脚本”和“更新成功”。

隔离注入系统目标复制失败：函数退出 0，当前文件为模拟新版本 3.7.19，快捷命令对应文件仍为 3.7.18，输出却声称同步成功。所有目标均为临时文件，未覆盖真实脚本。

建议：分别备份两个目标，暂存并校验后发布；第二目标失败应恢复一致状态或明确报告部分失败，不能提前记为完整成功。

## 高风险设计与优化建议（不冒充新漏洞）

- `nft.sh:862` 的“安装 nftables”在已经安装时选择完整接管，会备份配置后 `nft flush ruleset`。它有明确确认提示，因此不是未经确认的静默清空；但全局清空可能影响 Docker、其他防火墙及 Snell 计数表。建议提供仅管理本脚本表的模式，并区分文件备份和运行时规则备份。没有实际执行此分支。
- 大量用户数据通过八列字符串传递，字段扩展容易引入类似 v3.7.18 的解析问题。建议保留已有显示接口兼容，逐步让内部路由/配置逻辑读取结构化 JSON，不做一次性大重构。
- Xray/Sing-box 的超额用户逐个应用配置，同一轮多用户超额会重复重建、重启同一核心。建议先收集同核心状态变更，再一次校验和应用；需保留逐用户送达状态和整批失败回滚。此项为源码确认的批量处理优化，未测量大量用户的实际耗时。
- 用户变更和核心切换的私有备份缺少统一容量概览和保留策略；长期频繁操作会累积文件。建议增加容量提示及可配置清理入口，不能无提示清除可回退数据。
- 上次已说明的最后一次统计采样到核心停止之间的微小计量窗口仍存在；不能承诺严格零漏计。真实 Telegram、完整 Alpine/OpenRC、HY2/TUIC 客户端等验证边界仍不能由当前本地回归代替。
