# 链式代理主备故障转移

负载均衡组新增策略**主备故障转移**（`failover`）。组里的节点按优先级排列：

- 第一优先节点可用时走它；
- 不可用时，依次使用下一个可用节点；
- 所有节点都不可用时走**直连**（出口变为服务器自己的 IP）；
- 高优先级节点恢复后，连续 3 次检测可用才切回，避免在不稳定的节点之间来回抖动。

切换由常驻服务 `vless-failover` 在运行时完成，**不重启内核，不影响其他用户的连接**。

## 使用

1. `vless` → 分流管理 → 链式代理 → `7` 创建负载均衡组 → `4` failover，选择节点时**按优先级顺序**输入编号（如 `3 1 2`，先写的优先），确认优先级后保存。创建后监控服务自动启用。
2. 在**分流规则**中选择该组作为出口，或在用户管理里把**用户路由**设为该组（Xray、sing-box 协议的用户都支持）。
3. 查看状态：链式代理 → `8` 查看负载均衡组，或执行 `vless --failover-status`。手动检查一轮：`vless --failover-check`。
4. 检测网址：链式代理 → `12` 故障转移检测网址。

删除最后一个故障转移组后，监控服务自动停止并移除。

## "可用"的判定

经该节点访问**每一个**检测网址都能收到 HTTP 响应，节点才算可用。默认网址：

- `https://www.gstatic.com/generate_204`
- `https://cp.cloudflare.com/generate_204`

只测一个网址是不够的。在测试服务器上，真实节点 LC-KDDI 访问 gstatic 只要 46 毫秒，但访问 Cloudflare 背后的网站全部超时。只测 gstatic 时它会被当作可用节点选中，实际上大部分网站都打不开。检测网址最多 5 个，可以按自己实际访问的网站调整。

## 切换时机

- **检测周期**：每 10 秒一轮，各节点并行探测，每个网址最多等 8 秒。存在半故障节点时，一轮会拉长到约 18 秒。
- **切走**：当前节点一轮检测不可用就立即切到下一个可用节点（或直连）。服务器实测约 16～21 秒。
- **切回**：更高优先级的节点需连续 3 轮可用才切回。服务器实测约 36～55 秒。
- 每次切换写入 `/etc/vless-reality/failover.log`，并通过管理员 Telegram 通知（已启用 TG 通知时）。

## 工作原理

两个内核都没有原生的"按顺序故障转移"（Xray 的 `leastLoad` 权重不保证优先级，sing-box 只有 `selector` 和 `urltest`），所以由监控服务决定出口：

- **Xray**：故障转移组渲染为 `leastLoad` 均衡器（`fallbackTag: direct`）。组内每个节点另有一个只监听 `127.0.0.1`、带随机密码的 SOCKS 探测入口（`fo-probe-*`，端口从 61800 起，避开数据库、配置中已用的端口，以及其他进程正在监听的 TCP 端口），路由只走对应节点。监控经这些入口探测，用 `xray api bo` 指定出口，全部不可用时指定 `direct`。均衡器自带的健康检查（只用第一个检测网址）作为监控未运行时的保底。配置中只在存在故障转移组时开启 RoutingService。
- **sing-box**：渲染为 `selector`，候选出口为 [节点…, direct]。监控经只监听本机、带随机密钥的 Clash API（`127.0.0.1:10087`）对每个网址做延迟测试，再切换 selector。内核未编入 `with_clash_api` 时不写入 Clash API，组固定使用第一优先节点。
- 密码和密钥分别保存在 `/etc/vless-reality/failover-probe.secret`、`singbox-clash-api.secret`（600），通过 stdin 交给 curl，不出现在进程参数中。
- Xray 重启会丢失指定，监控会在下一轮静默补上；重启期间探测入口还没就绪（curl 返回 7/97）时，整组跳过这一轮，不会误判为全部不可用。
- 跳过的原因记为该组的"最近异常"（状态页可见）。同一异常持续时日志只记一次，恢复后记一行"检测恢复正常"。
- 组内节点及优先级以内核配置为准（Xray 均衡器的 `selector`、sing-box selector 的候选），不读数据库。节点改名后、配置重建完成前，数据库已是新名字而配置还是旧的，读数据库会把新名字的节点当作不存在，误切到低优先级节点（真机发现）。
- 上一轮的出口已不在组内（节点改名、删除或移出组）时按首次检查静默重新选择，不发"不可用"通知。组不再被分流规则或用户路由引用时，其状态在下一轮清除。

## sing-box 用户路由

sing-box 协议用户的用户路由可以设为任意负载均衡组（`balancer:组名`），故障转移组也包括在内：

- 渲染时生成 `auth_user` 规则指向组出站 `balancer-组名`，排在全局分流规则之前。
- 组出站和节点出站由分流规则与用户路由共用的 `_singbox_append_balancer_outbounds` 生成，两处结果一致：节点 tag 固定为 `chain-节点-prefer-ipv4`。监控服务直接读取组出站的候选列表。有全局分流规则时复用已生成的组；没有时只为用户路由引用到的组补生成，不会重复生成出站。
- 只被用户路由引用的故障转移组同样写入 Clash API，监控服务按 `singbox.json` 中的 selector 识别并切换。
- 用户路由指向已删除的组，或是 sing-box 不支持的路由类型时，渲染会给出提示（同时写入日志），该用户按全局规则走，不再静默忽略。
- 组内节点全部无效的 leastPing / random / roundRobin 组候选为空，sing-box 会拒绝整份配置；用户路由遇到这种组同样提示并让该用户按全局规则走，不会因为一个用户卡住所有配置变更。故障转移组的候选总带 `direct`，不受影响。

## 顺带修复（同一处代码）

- Xray 健康检查原先按第一个节点名的前缀拼通配符，名字不同的节点不会被探测；只有用户路由时完全不生成健康检查。现在按配置中实际存在的均衡器精确列出节点。
- 均衡器只引用成功生成出站的节点：节点已被删除时，不再引用不存在的出站。注意 sing-box 1.14.0 的 `check` 不校验 tag 引用（候选、`default`、路由规则出站、`final` 指向不存在的 tag 都返回 0），这类错误要到启动时才暴露，测试里需另外校验引用。
- 创建负载均衡组时拒绝重名或含 `|` 的组名。
- sing-box 分流规则原先把出口写成 `balancer:组名`，而组出站的 tag 是 `balancer-组名`。`sing-box check` 不检查规则引用的出站，所以配置校验能通过，但运行时命中规则的连接会报 `outbound not found` 而失败。所有策略的组在 sing-box 分流规则下都受影响。现已改为与 Xray 一致（移植自 `d39aada`）。

## 限制

- 检测网址是全局设置，所有故障转移组共用。
- 监控服务停止时：Xray 保持最后一次指定，sing-box 保持最后选中项；内核重启后 Xray 回到保底逻辑。
- sing-box 下的 random / roundRobin 组原先实际固定使用第一个节点，分流规则引用组时出站名写错；两者已修复（random / roundRobin 改为按最低延迟的 urltest，sing-box 内核不支持按连接随机或轮询），见 [singbox-balancer-strategies.md](singbox-balancer-strategies.md)。
- 有全局分流规则时 sing-box 会生成所有组：节点全部无效的 leastPing / random / roundRobin 组即使没被引用，也会让整份 sing-box 配置被 `check` 拒绝（`missing tags`，原有问题，已用真实 sing-box 1.14.0 复现，本版不修改）。

## 测试

### 本地（WSL Ubuntu 24.04，jq 1.7.1）

`tests/chain-failover.sh` 共 9 部分：
- 两条 Xray 渲染路径与 sing-box 渲染（用真实 Xray 26.11.9 的 `run -test` 和 sing-box 1.14.0 的 `check` 校验）；
- 决策逻辑；
- Xray 与 sing-box 监控：切换、半故障节点识别、显式直连、稳定切回、重启后补指定、失败重试、未就绪跳过、密钥不进参数；
- 服务定义、检测网址校验；
- 删除组后配置事务不再拒绝；
- 两个内核配置的引用完整性：规则、分组、均衡器引用的出站都必须存在。

运行时验证：用真实 sing-box 1.14.0 组成"客户端 → 服务端 SS2022 入站 → 分流规则 → 故障转移组 → 链式节点 A"的完整链路。修复前访问 example.com 失败，服务端报 `outbound not found: balancer:FO`；修复后返回 HTTP 200，落地节点 A 收到连接。

全量回归：通过 59、失败 3、跳过 6。失败与跳过项和 main 基线相同，都是环境原因（见 [upstream-sync-v3.7.20-preview.md](upstream-sync-v3.7.20-preview.md)）。

`tests/singbox-user-balancer.sh`（sing-box 用户路由支持负载均衡组，2026-11-25）共 4 部分：
- 无全局分流规则：故障转移 selector、leastPing urltest 及节点出站照样生成，`auth_user` 规则指向组，写入 Clash API；组不存在、组内没有可用节点、路由类型不支持三种情况都有提示，且不生成规则；
- 有全局分流规则：复用已生成的组，出站 tag 不重复，用户规则排在全局规则之前；
- 监控服务能识别只被用户路由引用的故障转移组；
- 用户路由菜单能选到负载均衡组。

生成的配置都通过真实 sing-box 1.14.0 `check`，另做 tag 引用完整性校验（`check` 不查引用）。该测试在改动前的代码上失败。另外用真实内核手动启动了生成的配置：两份都正常启动；经 Clash API 能读到并切换只被用户路由引用的 `balancer-FO`（候选 [B, A, direct]，PUT 返回 204），不带密钥返回 401。

加入该测试后全量回归：通过 60、失败 3、跳过 6，比上面多出的 1 项通过就是新测试，失败与跳过项相同（本轮另设置了 `XRAY_RELEASE_TEST_ARCHIVE`，`xray-release-native.sh` 照常通过）。

### 真机（Debian 12，jq 1.6，Xray 26.3.27）

`tests/chain-failover.sh` 在服务器上同样通过。端到端测试在 VLESS REALITY 入站上添加两个测试用户，未改动原有 4 条分流规则：

- 组 1：[本地可控节点 FO-Local → LC-KDDI → LC-GLBB-Mini]；
- 组 2：[FO-Local]。

| 阶段 | 组 1 | 组 2 | 客户端实测出口 |
|---|---|---|---|
| FO-Local 正常 | FO-Local；可用节点不含半故障的 LC-KDDI | FO-Local | 服务器 IP |
| 停止 FO-Local | 16 秒后跳过 LC-KDDI，切到 LC-GLBB-Mini | 16 秒后直连 | 组 1：LC-GLBB-Mini 的出口 IP，组 2：服务器 IP |
| 恢复 FO-Local | 连续 3 轮可用后（55 秒）切回 | 同时切回 | 服务器 IP |

整个过程中 Xray 只在添加测试用户时重启过一次。测试结束后删除测试用户、组和节点，`config.json` 与测试前一致。

真机发现并已修复的问题：
- jq 1.6 对空输入配合 `-e` 返回 0，导致状态文件被写空、每轮都当作首次检查；
- 只测一个网址会选中半故障节点；
- 配置事务把探测入口计入必须保留的入站，导致删除组后新配置被拒绝。

**未验证**：
- sing-box 故障转移未在真机端到端测试。本地已用真实 sing-box 验证分流规则到故障转移组的转发；监控经 Clash API 测速与切换，只验证了原型和模拟测试。
- 测试服务器未启用 TG 通知，通知只在模拟测试中验证。
- 未在 Alpine / OpenRC 上实测服务。
- 未测试与多 IP 路由、按端口路由同时使用的组合。
