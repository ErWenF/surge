# v3.7.15 Telegram Bot 优化

本文记录 v3.7.15。v3.7.16 已改为默认单向流量，并区分 `/traffic` 与 `/status`；见 [后续调整](tg-bot-query-2026-10-14.md)。

基线：`12f348c`。本轮集中修改 Telegram 配置、消息处理、通知送达判断和对应服务；复用 Bash、curl、jq，不引入 Web 服务、公开端口、域名、证书或新的产品运行依赖。Python 仅用于隔离测试。

## 管理员与用户使用

管理员 Bot 用于接收告警、过期提醒和日报；用户 Bot 用于私聊绑定、个人用量和状态查询。新增独立用户 Token，管理员通知仍使用原 Token。旧配置留空时继续复用管理员 Bot，已有用户、端口、配额和 Telegram 绑定保留。

1. 在 `@BotFather` 创建专用用户 Bot。
2. 运行 `vless` → `4 用户管理` → `t TG 通知配置` → `8 用户查询机器人`。
3. 用户机器人原先已启用时，先选择 `1` 禁用。选择 `7` 设置独立 Token，再选择 `1` 启用。
4. 管理员选择 `2` 为指定用户生成一次性绑定码，把 `/bind 绑定码` 发给该用户。绑定码有效期 24 小时，重新生成后旧码失效。
5. 用户打开用户 Bot 的私聊，发送绑定命令后使用 `/traffic`、`/status`、`/unbind`、`/help`。管理员可查看和解除绑定，或单独重启 Bot 消息服务。
6. 管理员选择菜单 `8 设置某个用户的单向/双向显示`，按核心、协议和带端口的用户列表选择用户，然后设置单向净流量、双向估算或沿用默认。设置立即生效，无需重启节点或 Bot。

一个 Telegram 私聊目前绑定一个脚本用户；同一核心、同一协议下的旧数据若出现重复用户名，会拒绝自动匹配，避免查询或解绑另一个端口的账号。查询展示的是当前周期累计用量、配额、端口、周期、停用原因和最后同步时间；未新增历史账单或网页面板。

## 单向与双向显示

按另一聊天中已确认的 VPS 计费语境，“服务器双向”指服务器的入站＋出站，包含代理转发的两段。当前命名用户统计记录的是上传＋下载的净流量。普通代理转发时，服务器双向消耗近似于净流量的两倍，但这个换算不包含报头、加密、重传和其他业务，不能等同于服务商实际账单。

- 单向显示：显示保存的用户净用量、净配额及净剩余量。
- 双向估算：已用量、总配额和剩余量一起乘 2，百分比保持不变；报告明确写“服务器双向估算（净流量×2）”。
- 每个用户的 `telegram_traffic_view` 独立保存，兼容单端口对象和多端口数组。两个同协议端口上的不同用户可以使用不同显示口径。清除该字段后沿用服务器默认 `user_bot_traffic_view`；v3.7.15 默认双向估算，v3.7.16 默认单向。
- 开关仅由管理员在服务器上的管理菜单设置；用户 Bot 没有修改口径的命令，用户查询只读取管理员保存的选择。
- 开关仅影响 TG 查询显示，不重新计算历史用量，不修改数据库中的 `used`、`quota` 或用户启停状态，也不更改统计、周期重置和超额停用逻辑。管理员日报和额度通知仍明确使用净流量口径。
- TG 查询使用 KiB / MiB / GiB / TiB 正确标记原有二进制单位。原菜单的 `250G` 净配额实际为 250 GiB，双向估算显示 500 GiB，约 536.87 GB；不是官网十进制的 500 GB。

例如净用量 100 GiB、净配额 250 GiB，在双向模式下显示已用 200 GiB、总配额 500 GiB、剩余 300 GiB，使用率仍为 40%。超额停用仍以净用量是否达到 250 GiB 判定。

## 响应与升级

- 用户消息改为系统服务持续长轮询，`getUpdates` 等待 20 秒；收到消息即可返回并处理，不再等到下一个整分钟。接口失败以 2～30 秒退避，日志不记录 Token。
- 支持 systemd 和 OpenRC `supervise-daemon`；旧的 `--tg-bot-poll` 单次入口保留。已有安装重新运行更新后的脚本时，会尝试将启用的用户 Bot 迁移为常驻服务。主进程直接等待实际持锁的轮询进程；收到停止信号后等待其清理，清理期间忽略重复停止信号，防止服务退出时留下锁。
- 更新服务先保存原定义及运行、自启状态；新服务启动并检查通过后才移除旧 Bot cron。启动、服务检查、停止、自启设置或 cron 操作失败时恢复原状态；回滚本身失败会明确报错并保留可用备份。
- 不更改流量统计任务的频率。已绑定用户的 `/traffic` 查询会尝试同步；同批查询及五秒内的连续查询复用成功同步结果。未绑定用户不能触发统计；同步失败会标明报告来自已保存用量。
- 无需卸载或重建节点；迁移只启停 Bot 服务。常驻 Bot 服务文件标记脚本版本，后续更新后重新进入脚本会更新服务定义并重启 Bot。

同一个用户 Bot 只能由一台服务器负责轮询；多服务器共用一个用户 Token 会产生 API 409 冲突。管理员仅发送通知的 Bot 可以共用。设置或启用用户 Bot 会检查身份及 webhook；已有 webhook 时拒绝占用，保留其他程序的 webhook。

## 安全与通知可靠性

- Token 输入隐藏，菜单仅显示配置状态；Token 经标准输入交给 curl，不出现在其进程命令行。配置仍保存于仅 root 可读的 `telegram.json`，并以锁和原子替换更新。
- 绑定在数据库写锁内再次检查用户唯一性、Chat ID、一次性码及有效期；重复 Chat ID 或存在歧义的用户拒绝映射。
- 管理员、用户及旧版通知共用 URL 编码的纯文本发送路径，检查 Telegram 的 `.ok`；按最多 2000 个 Unicode 字符拆分，中文、emoji 和 `LANG=C` 均可用。支持管理员群组的负 Chat ID。
- 暂时发送失败不推进消息 offset，稍后重试；用户屏蔽 Bot 或聊天失效等 API 400/403 错误跳过该条，避免阻塞其他用户。
- 更换 Bot 身份重置 offset，同一个 Bot 轮换 Token 保留 offset；更换用户 Token 必须先禁用。管理员 Token 被运行中的用户 Bot 复用时，菜单阻止直接替换。
- 流量提醒、超额通知、临近过期提醒和日报仅在发送成功后记录送达状态。超额停用继续执行，未送达的超额消息从保存用量补发，不重复停用用户。日报允许在当天定点之后跨小时补发。

## 边界

- Telegram 请求使用隔离的本地 HTTP 模拟接口，没有真实 Token，也未向真实 Telegram 发送消息。实际响应时间还取决于 Telegram 网络及统计同步耗时，不能保证每次立即回复。
- systemd 服务已在 HK 实测；OpenRC 服务生成及语法通过，但完整 Alpine / OpenRC 生命周期、真实 Telegram 集成仍待验证。
- 重试可能重复消息或已成功发送的长消息分段；管理员与用户送达状态尚未分别记录。已过期后的禁用通知仍按事件发送，未新增持久化补发队列。
- Bot 的消息处理只保证 Telegram 队列内的重试，不承诺永久保存离线消息。查询缓存最长五秒，不是逐字节实时计费。
- 服务器验证期间只操作隔离目录，未替换线上脚本或修改 Git remote。2026-10-14 已将验证版本推送到上述预览分支，并按用户要求同步到 `main`，供用户自行更新并测试真实 Telegram；HY2 / TUIC 客户端端到端测试继续按此前安排暂缓。
